# Практическая работа. Исследование индексов в Microsoft SQL Server

## 1. Цель и постановка задачи

Цель работы — изучить, как индексы SQL Server влияют на поиск и чтение строк, а также на добавление новых записей. Для проверки используется таблица Customers с 50 000 исходных записей. В ходе работы сравниваются запросы до создания индексов и после добавления кластерного и некластерных индексов.

Для оценки производительности в SQL Server Management Studio включаются SET STATISTICS IO и SET STATISTICS TIME. Первая команда выводит сведения о логических и физических операциях чтения, вторая — время выполнения и процессорное время. Фактические значения зависят от оборудования, настроек сервера, состояния кэша и плана выполнения, поэтому их нужно снимать на той системе, где выполняется работа.

## 2. Создание таблицы и тестовых данных

База данных IndexDemo создаётся отдельной командой, после чего в ней создаётся таблица dbo.Customers. Поле CustomerID имеет свойство IDENTITY(1,1), то есть SQL Server автоматически выдаёт ему последовательные значения, начиная с 1. При этом IDENTITY само по себе не создаёт ни первичный ключ, ни индекс — в начальном состоянии таблица остаётся кучей (heap), пока не будет создан кластерный индекс.

Поля таблицы Customers:

CustomerID (INT IDENTITY(1,1)) — Автоматически генерируемый идентификатор клиента.

Email (NVARCHAR(100)) — Адрес электронной почты; используется в точечном поиске.

LastName (NVARCHAR(50)) — Фамилия клиента.

FirstName (NVARCHAR(50)) — Имя клиента.

City (NVARCHAR(50)) — Город; используется для проверки менее избирательного фильтра.

RegistrationDate (DATE) — Дата регистрации.

Notes (NVARCHAR(500), NULL) — Дополнительный текст; увеличивает размер строки.

Исходная вставка формирует 50 000 строк. Email строится из номера строки и получает уникальный на вид адрес userN@example.com. Фамилии, имена, города и даты создаются псевдослучайно. Город выбирается из пяти вариантов, поэтому каждый город в среднем должен встретиться примерно в 20 % строк. Это ожидаемая доля, а не гарантия точного равенства распределения.

В поле Notes записывается строка из 500 символов N'A'. Поскольку поле имеет тип NVARCHAR, она занимает заметную часть строки и делает запросы с SELECT * более затратными по объёму данных, чем запросы, возвращающие только несколько столбцов.

```sql
SELECT COUNT(*) AS TotalRows
FROM dbo.Customers;
```

После заполнения ожидается результат TotalRows = 50000. Если число отличается, сначала следует проверить, не запускалась ли вставка повторно и не остались ли данные от предыдущего опыта.

## 3. Поиск до создания индексов

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
SELECT CustomerID, Email, LastName
FROM dbo.Customers
WHERE Email = 'user12345@example.com';
```

Этот запрос ищет одну запись по точному совпадению Email. В начале таблица не имеет ни кластерного, ни некластерного индекса, поэтому SQL Server, как правило, вынужден просмотреть строки таблицы последовательно. В плане выполнения обычно отображается Table Scan. Даже если найденная запись располагается близко к началу физического хранения, сервер не может считать, что она единственная, пока не проверит остальные строки, поскольку уникальность Email ограничением не задана.

В выводе STATISTICS IO особенно полезно смотреть logical reads — число страниц данных, прочитанных из буферного кэша. Чем больше страниц приходится просматривать, тем выше объём работы. Physical reads могут быть равны нулю, если страницы уже находятся в памяти; это не означает, что запрос не читал данные. В STATISTICS TIME сравнивают elapsed time (общее прошедшее время) и CPU time (процессорное время). На коротком запросе значения могут быть очень маленькими и заметно колебаться между запусками.

### Как корректно провести сравнение

- Запустить исходный запрос и сохранить вывод из вкладки Messages, а также фактический план выполнения.

- После добавления соответствующего индекса выполнить тот же запрос с теми же параметрами.

- Сравнить прежде всего logical reads и выбранный оператор плана; время использовать как дополнительный показатель.

- Сделать несколько запусков и учитывать кэш. Не стоит сравнивать первый холодный запуск одного варианта с прогретым запуском другого.

Важно. SET STATISTICS IO/TIME выводит диагностические сообщения, а не меняет сами данные. Команды продолжают действовать в текущем соединении, пока их не выключить командами SET STATISTICS IO OFF и SET STATISTICS TIME OFF.

## 4. Кластерный индекс по CustomerID

```sql
CREATE CLUSTERED INDEX CIX_Customers_CustomerID
ON dbo.Customers (CustomerID);
GO
EXEC sp_helpindex 'dbo.Customers';
```

Кластерный индекс организует строки таблицы в соответствии с ключом CustomerID. Для обычной таблицы SQL Server может существовать только один кластерный индекс, потому что он определяет порядок хранения строк в индексной структуре. После его создания таблица уже не является кучей. Индекс не объявлен UNIQUE, хотя значения IDENTITY в этом опыте последовательно генерируются и не повторяются. Свойство IsUnique описывает определение индекса, а не только фактические значения, которые сейчас лежат в таблице.

sp_helpindex показывает индексы таблицы, в том числе их имена и типы. Для этого этапа ожидается CIX_Customers_CustomerID как clustered index. Создание кластерного индекса требует упорядочить существующие строки, поэтому эта операция сама по себе тоже выполняет работу и может потребовать времени и дополнительного места на диске.

### 4.1. Поиск по идентификатору

```sql
SELECT CustomerID, Email, LastName
FROM dbo.Customers
WHERE CustomerID = 12345;
```

Так как CustomerID является ключом кластерного индекса, SQL Server может найти нужную запись по навигации по B-дереву. Для такого фильтра ожидается Clustered Index Seek вместо полного просмотра таблицы. Выбирается только одна запись, поэтому обращение к индексу хорошо подходит задаче. Однако фактический оператор нужно подтвердить в плане выполнения: оптимизатор выбирает его на основании статистики и оценки стоимости.

### 4.2. Поиск по диапазону

```sql
SELECT CustomerID, Email
FROM dbo.Customers
WHERE CustomerID BETWEEN 10000 AND 10100;
```

Условие BETWEEN включает обе границы. Если исходные идентификаторы представлены без пропусков, запрос возвращает 101 строку: значения от 10000 до 10100 включительно. Кластерный индекс позволяет найти первую запись диапазона и затем прочитать следующие записи последовательно по ключу. Это пример, когда индекс полезен не только для поиска одной строки, но и для выборки диапазона.

## 5. Некластерный индекс по Email

```sql
CREATE NONCLUSTERED INDEX NCIX_Customers_Email
ON dbo.Customers (Email);
GO
DROP INDEX NCIX_Customers_Email ON dbo.Customers;
CREATE NONCLUSTERED INDEX NCIX_Customers_Email
ON dbo.Customers (Email) INCLUDE (LastName);
GO
```

Некластерный индекс хранит отдельную индексную структуру, отсортированную по Email. Он позволяет быстро находить диапазон значений Email, не просматривая все записи основной таблицы. Сначала индекс создаётся без дополнительных столбцов, затем удаляется и создаётся повторно с INCLUDE (LastName). Это сравнение структуры индекса: INCLUDE добавляет LastName на листовой уровень, но не делает его частью ключа сортировки.

```sql
SELECT CustomerID, Email, LastName
FROM dbo.Customers
WHERE Email = 'user12345@example.com';
```

В итоговом запросе фильтр выполняется по Email, а результат содержит Email, LastName и CustomerID. Email входит в ключ некластерного индекса, LastName включён через INCLUDE. Поскольку таблица имеет кластерный индекс, значение кластерного ключа CustomerID также хранится в некластерном индексе как локатор строки. Поэтому для этого запроса индекс может покрывать все необходимые столбцы, и отдельный Key Lookup обычно не требуется. В плане ожидается Index Seek по NCIX_Customers_Email.

Почему INCLUDE полезен. Включённые столбцы позволяют вернуть данные из самого индекса, не расширяя его ключ сортировки. Это особенно удобно для узких поисковых запросов, но увеличивает размер индекса и стоимость его обслуживания при изменении включённых данных.

## 6. Индекс по City и выборка около 20 % таблицы

```sql
CREATE NONCLUSTERED INDEX NCIX_Customers_City
ON dbo.Customers (City);
GO
SELECT *
FROM dbo.Customers
WHERE City = N'Москва';
```

Индекс по City создаёт возможность быстро находить строки с заданным городом. Однако запрос возвращает все столбцы, включая Notes, а Москва в среднем составляет примерно пятую часть таблицы. Это менее избирательный фильтр, чем поиск по одному Email. После нахождения ключей индекса серверу пришлось бы получать остальные столбцы для большого числа строк, если индекс их не содержит.

В таком случае оптимизатор может посчитать более дешёвым просмотр кластерного индекса целиком (Clustered Index Scan), чем проход по индексу City с последующими многочисленными Key Lookup. Поэтому наличие индекса не означает, что любой запрос обязательно будет его использовать. Решение зависит от оценки количества строк, ширины строки, статистики и стоимости чтения страниц.

Тот факт, что City состоит всего из пяти вариантов, снижает избирательность индекса. Для запросов, возвращающих только City и, например, CustomerID, индекс может быть полезнее; для SELECT * его преимущество значительно меньше. Чтобы подтвердить вывод, следует посмотреть фактический план выполнения и число logical reads, а не делать заключение только по наличию индекса.

## 7. Влияние индексов на вставку данных

Далее выполняются две вставки по 1000 строк. Первая проводится, пока у таблицы есть кластерный индекс и два некластерных индекса — Email и City. После неё некластерные индексы удаляются, а кластерный сохраняется. Затем выполняется вторая вставка такого же объёма. Такая последовательность позволяет оценить накладные расходы на поддержку дополнительных индексов.

```sql
-- Первая вставка: кластерный + два некластерных индекса
INSERT INTO dbo.Customers (Email, LastName, FirstName, City, RegistrationDate, Notes)
SELECT TOP (1000)
'newuser' + CAST(ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) AS NVARCHAR(10)) + '@test.com',
'NewLast' + CAST(ABS(CHECKSUM(NEWID())) % 100 AS NVARCHAR(10)),
'NewFirst' + CAST(ABS(CHECKSUM(NEWID())) % 100 AS NVARCHAR(10)),
N'Москва', GETDATE(), REPLICATE(N'B', 500)
FROM sys.all_objects;
GO
DROP INDEX NCIX_Customers_Email ON dbo.Customers;
DROP INDEX NCIX_Customers_City ON dbo.Customers;
-- Вторая вставка: остаётся только кластерный индекс
INSERT INTO dbo.Customers (Email, LastName, FirstName, City, RegistrationDate, Notes)
SELECT TOP (1000)
'newuser2_' + CAST(ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) AS NVARCHAR(10)) + '@test.com',
'NewLast' + CAST(ABS(CHECKSUM(NEWID())) % 100 AS NVARCHAR(10)),
'NewFirst' + CAST(ABS(CHECKSUM(NEWID())) % 100 AS NVARCHAR(10)),
N'Москва', GETDATE(), REPLICATE(N'B', 500)
FROM sys.all_objects;
GO
```

При первой вставке SQL Server должен добавлять новые записи в кластерную структуру и обновлять оба некластерных индекса. При второй вставке остаётся обновить только кластерный индекс. Поэтому обычно ожидается, что вариант без дополнительных индексов будет вставлять строки быстрее и выполнять меньше работы по обслуживанию структур. Но разница в миллисекундах может быть небольшой или нестабильной; на неё влияют кэш, журнал транзакций, фоновые задачи и другие процессы.

Ограничение эксперимента. Вставки не полностью идентичны по тексту Email: во втором наборе есть дополнительный префикс newuser2_. Для более строгого теста стоит повторять эксперимент несколько раз, одинаково формировать значения и сравнивать среднее время, сохранив при этом смысл этапа — наличие или отсутствие двух некластерных индексов.

## 8. Проверка свойств индекса

```sql
EXEC sp_helpindex 'dbo.Customers';
SELECT
INDEXPROPERTY(OBJECT_ID('dbo.Customers'), 'CIX_Customers_CustomerID', 'IsClustered') AS IsClustered,
INDEXPROPERTY(OBJECT_ID('dbo.Customers'), 'CIX_Customers_CustomerID', 'IndexDepth') AS IndexDepth,
INDEXPROPERTY(OBJECT_ID('dbo.Customers'), 'CIX_Customers_CustomerID', 'IsUnique') AS IsUnique;
```

### Результаты проверки свойств индекса

IsClustered — Является ли индекс кластерным. Для CIX_Customers_CustomerID ожидается 1.

IndexDepth — Глубину индексного дерева. Значение зависит от количества страниц и данных; это не фиксированная константа.

IsUnique — Задан ли индекс как уникальный. Для созданного без UNIQUE индекса ожидается 0.

IndexDepth отражает число уровней структуры B-дерева и зависит от объёма таблицы, размера ключа и организации страниц. Нельзя заранее утверждать, что глубина всегда будет равна одному конкретному числу. IsUnique также не следует трактовать как прямую проверку отсутствия повторов в текущих данных: это свойство определения индекса. В данном скрипте индекс создан без параметров UNIQUE и PRIMARY KEY.

## 9. Возвращение некластерных индексов

```sql
CREATE NONCLUSTERED INDEX NCIX_Customers_Email
ON dbo.Customers (Email) INCLUDE (LastName);
CREATE NONCLUSTERED INDEX NCIX_Customers_City
ON dbo.Customers (City);
```

В конце оба некластерных индекса создаются повторно. Это возвращает таблицу к состоянию с тремя индексами и позволяет ещё раз посмотреть их через sp_helpindex. При повторном запуске скрипта подряд необходимо учитывать текущее состояние базы: создание уже существующих базы, таблицы или индексов приведёт к ошибке. Перед повторным опытом следует либо удалить учебную базу и создать её заново, либо выполнять этапы в правильном порядке и предварительно проверять наличие объектов.

## 10. Небольшие замечания к исходному скрипту

- IDENTITY не заменяет ограничение PRIMARY KEY. Если CustomerID должен гарантированно быть уникальным на уровне базы, это лучше явно закрепить первичным ключом или UNIQUE-ограничением. В рамках данного упражнения индекс создаётся отдельно, чтобы показать его свойства.

- Выражение ABS(CHECKSUM(NEWID())) теоретически может столкнуться с переполнением на минимальном отрицательном значении INT. Риск крайне мал, но для надёжного генератора можно преобразовать CHECKSUM в BIGINT перед ABS или использовать другой способ получения неотрицательного числа.

- TOP (1000) без условия ORDER BY выбирает произвольные 1000 строк из источника. В демонстрации это приемлемо, потому что важен объём вставки, но для детерминированного набора тестовых данных лучше использовать явный генератор чисел.

- Перед сравнением запросов полезно включить отображение фактического плана выполнения. По одним только времени и логическим чтениям не всегда понятно, почему оптимизатор выбрал конкретный путь.

```sql
CustomerID = 12345 после CIX. Ожидаемое поведение: Поиск по ключу кластерного индекса. Что проверить в SSMS: Clustered Index Seek и число прочитанных страниц.
```


Первая и вторая вставки по 1000 строк. Ожидаемое поведение: С двумя дополнительными индексами обычно больше операций поддержки. Что проверить в SSMS: Elapsed time и CPU time при повторных сравнимых запусках.

```sql
INDEXPROPERTY для CIX. Ожидаемое поведение: Подтверждение типа, глубины и уникальности индекса. Что проверить в SSMS: IsClustered = 1; IsUnique = 0; фактический IndexDepth.
```

## 12. Итоговый вывод

В ходе работы рассматривается разница между таблицей без индексов и таблицей с индексными структурами. До создания индексов точечный поиск по Email обычно требует последовательного просмотра таблицы. Кластерный индекс по CustomerID упорядочивает строки по идентификатору и ускоряет поиск по одному значению и диапазону. Некластерный индекс по Email эффективен для точечного поиска, а INCLUDE (LastName) позволяет покрыть выбранные столбцы и избежать дополнительного обращения к основной структуре данных.

Индекс по City не гарантирует ускорение запроса SELECT *: фильтр возвращает значительную часть строк и включает широкий столбец Notes, поэтому полный просмотр кластерного индекса может оказаться дешевле большого количества обращений за отдельными строками. Это показывает, что при оценке индексов важно учитывать не только условие WHERE, но и число возвращаемых строк, список столбцов и фактический план выполнения.

Вставка данных также зависит от количества индексов. Каждый дополнительный индекс требует изменений при добавлении строк, поэтому он может повышать стоимость записи и занимать дополнительное место. На практике индексы подбирают под реальные запросы: оставляют те, которые дают измеримую пользу, и избегают избыточных индексов, замедляющих изменения данных.

Общий вывод. Кластерные и некластерные индексы помогают ускорять подходящие запросы, но не делают автоматически быстрее все операции. Корректная оценка строится на сочетании плана выполнения, logical reads, процессорного времени и повторяемых измерений на одинаковых данных.

### Команды для завершения измерений

```sql
SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;
```

Числовые показатели времени и чтения в отчёте не подменяются условными значениями: их следует брать из фактического окна Messages на используемом экземпляре SQL Server. Описанные выше результаты — ожидаемая картина работы оптимизатора; итоговый план может меняться в зависимости от состояния среды и статистики.
